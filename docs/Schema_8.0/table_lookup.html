How KR Homebase uses this table
In one sentence. lookup holds two kinds of rows: choice lists (one row per allowed value, pointed at by *_lookup_id columns in other tables) and settings rows (one row per firm-wide setting, its JSON kept in description). Both kinds let the firm add a choice or change a setting without changing the database shape. The category tells you which kind a row is: settings categories start with kr_.
1. Choice lists
  • One row per choice. category names the list, value is the machine word, label is what people see, sort_order orders the list, and is_active = 0 retires a choice without breaking old rows that still point at it.
  • Id rule: lk_<category or short form>_<value>, for example lk_payment_type_ach, lk_matter_status_archived, lk_relationship_child. Other tables store this id in a column ending in _lookup_id (see Relationships above), sometimes without a declared foreign key (see the developer note at the top).
  • Never delete a choice that rows may point at; set is_active = 0. (category, value) is unique.
  • Description is plain text explaining the choice (not JSON).

2. Settings rows (categories starting with kr_)
  • One row per setting (or one row per item, for themes). description holds the whole setting as a JSON object; label is its name; value is a short stable key.
  • Only the API reads or writes them, and it checks the JSON with a zod contract (packages/contracts) before it is used or saved. A field that is missing or invalid falls back to its default; a screen never trusts the raw text.
  • Shape changes need no migration: add a field to the JSON and to its contract, with a default. Settings written since Nov 2026 carry a schemaVersion, so a reader can tell old and new shapes apart.
  • Saving updates description and updated_at in the same batch as an audit_log row. is_active = 0 retires a row (a removed theme); readers ignore inactive rows.
  • Choices that belong to one person do not go here; they go in user_preference (one row per person and key). lookup is firm-wide.

Raw SQL
CREATE TABLE lookup (
    id            TEXT PRIMARY KEY,
    category      TEXT NOT NULL,
    value         TEXT NOT NULL,
    label         TEXT NOT NULL,
    description   TEXT,
    sort_order    INTEGER NOT NULL DEFAULT 0,
    is_active     INTEGER NOT NULL DEFAULT 1 CHECK (is_active IN (0,1)),
    created_at    TEXT NOT NULL DEFAULT (datetime('now')),
    updated_at    TEXT,
    UNIQUE (category, value)
);
Index SQL (2)
CREATE INDEX idx_lookup_active ON lookup(category, is_active, sort_order);
CREATE INDEX idx_lookup_category ON lookup(category);
