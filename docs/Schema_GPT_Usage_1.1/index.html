KR GPT Usage Database Schema 1.1

A separate Cloudflare D1 database for the KR Homebase GPT Gateway. The gateway Worker (apps/shared/gpt-workers/gpt-models-worker.ts) owns provider calls, credential access, token and cost accounting, and model-connection storage for the krhomebase application. Homebase never sees a provider key: the Super Admin screen sends an encrypted credential envelope, and reports return only whether a key exists. Scope: development prototype.

Separate database. This is not part of the Homebase operational database. Database: krhomebase_gpt_usage_dev, Worker binding: GPT_USAGE_DB. No foreign key crosses into Homebase. Built from the SQL files in the previous repository; the live database was not read.

Cautions
  • Secrets. gpt_llm_credential.key is the only secret. New values are a Worker-public-key-encrypted envelope; the Worker decrypts at call time. If Worker performance later requires it, credentials may move to Worker-managed secrets, at the cost of Super Admin runtime flexibility.
  • No enforced foreign keys. The four tables are linked only by matching text values (application_id, kr_gpt_connection_id, provider plus llm_model plus credential_name). The Worker must keep them consistent.
  • Documented rule not in the schema. The old docs say an application cannot have two connections with the same type, provider and model. The schema does not enforce that; add a UNIQUE index if the rule matters.
  • Money as REAL. Rates and costs are floating point. Round when reporting and avoid using them for billing-grade accounting.
  • Development only. The database is krhomebase_gpt_usage_dev. A reset-and-recreate script exists in the old repository; it deletes all GPT data and must never be run against anything but development.
  • Built from SQL files, not the live database. This space was built from Schema_GPT_Usage_1.1.sql in the old repository. The live database was not read. Run the export command in the README to confirm it matches.
