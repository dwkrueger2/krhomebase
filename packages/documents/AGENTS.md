## Purpose

`packages/documents` holds the printable billing documents: the invoice (Option 1 and Option 2), the Statement of Account and the Payment Receipt. It has their data shapes (`src/types.ts`), the letterhead built from the firm profile (`src/letterhead.ts`), the money, date and hour formatters (`src/format.ts`), the file name rule (`src/fileName.ts`), the three builders that turn a Billing record into a document (`src/invoiceData.ts`, `src/statementData.ts`, `src/receiptData.ts`) and the sample documents (`src/sampleData.ts`). Part 7b of `docs/API/Billing_Audit.md` added the React templates (`InvoiceReportOption1.tsx`, `InvoiceReportOption2.tsx`, `StatementOfAccountReport.tsx`, `PaymentReceiptReport.tsx`), their shared parts (`reportParts.tsx`), the `PrintDocument` primitives (`printDocument.tsx`) and the paper stylesheet (`print-document.css`: the `--kr-print-*` tokens and the Letter page geometry; the DM Sans fonts are declared by `apps/web/app/globals.css`). The browser half of the print library (pagination, the handoff) is `apps/web/components/printing/`. Part 7c added the email builders (`invoiceEmail.ts`, `statementEmail.ts`, `receiptEmail.ts`), the record-to-document helpers shared by the web print and the API email (`invoiceReportFromRecord`, `receiptFromRecord`), the statement and receipt file names, and the server render (`renderDocument.tsx`: the self-contained HTML the API sends to Browser Rendering, with `print-pdf.css` and the generated stylesheet `src/generated/documentCss.generated.ts`).

It exists because both apps need the same documents (decision B1, the requester, Nov 15, 2026): `apps/web` prints them in the browser, and `apps/api` renders them to PDF for email, including the receipt the pay Worker's webhook sends with no browser involved. `apps/api` may not import `apps/web`, so the documents live here.

The repository guides in the root (`AGENTS.md` and `AGENTS_01` to `AGENTS_06`) apply. This package is not a version track and stays at `1.0.0` (`AGENTS_01`): a change advances the API track, the web track or both, depending on which app uses the changed behavior.

## Rules

1. **Dependencies:** `@krhomebase/contracts`, and `react` and `react-dom` as peer dependencies (the app that renders the templates provides them). Nothing else at run time. Development only: the React types, `@types/node` (tests) and Tailwind 4 (`tailwindcss`, `@tailwindcss/node`, `@tailwindcss/oxide`, the web app's versions) for the stylesheet generator. No imports from `apps/*`, no Cloudflare types, no Node-only modules: the code runs in a Worker and in a browser.
2. **Pure.** No database, no request, no `fetch`. The clock is read only where a caller may pass the time instead (`statementDate`, `receiptDate`), so tests can fix it.
3. **Dates are calendar dates in the firm's time zone** (`FIRM_TIME_ZONE`, America/Chicago). `MM/DD/YYYY` and `YYYY-MM-DD` texts are read as calendar dates, never as UTC midnight; an instant (a `Date` or a text with a time) is shown as its date in the firm's time zone. A Worker runs in UTC, so the old `new Date(text)` habit would print the wrong day.
4. **Builders take the contract shapes** (`@krhomebase/contracts` `billing.ts`) through `Pick<...>`, so the web app's screen types (which add `isEmpty` or make a field optional) pass as they are.
5. **Ported code keeps its comments** (`AGENTS_04`). Each file's header names its old file and says what changed.
6. Imports inside `src/` use `.ts` extensions. Each entry point is its own export path (`@krhomebase/documents/invoice`); there is no index file.
7. Tests sit beside the code (`*.test.ts`, `*.test.tsx`; the templates are rendered with `react-dom/server`, a development dependency) and use made-up data only.
8. **The PDF stylesheet is generated:** after changing a template's classes, `print-document.css`, `print-pdf.css` or the fonts (in `apps/web/styles/fonts`), run `pnpm documents:css` from the repository root and commit the result. `renderDocument.test.ts` rebuilds it and fails when the committed one is stale.
9. **Templates stay pure:** no hooks, no browser APIs, no `'use client'`, so the API can render the same markup for the PDF (part 7c). Every visual block is a direct child of `PrintDocument` (a pagination unit); tables that may span pages use `PrintTable`. Colors are the `--kr-print-*` tokens, never `--kr-theme-*`: paper does not change with a person's theme. Tailwind classes here are generated by the web app's Tailwind (`@source` in `apps/web/app/globals.css`).

## Invoice tax

Tax line (the requester, Nov 16, 2026, repository patch 54): `InvoiceReportData.taxAmount` (from `BillingInvoice.taxAmount`, missing = 0) is added to `totalAmount` by the builders and printed as a "Tax" row (both invoice options and the invoice email) only when above zero.
